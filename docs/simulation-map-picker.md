# 模拟定位·地图选点（1.5.4）

## 做了什么

模拟定位原来只能回放 `location-sample.json` 里的一份样本（正常来自本机采样的 Windows
定位）。现在在 **寝室打卡 → 定位来源与登录** 卡片里多了一个 **在地图上选择位置** 按钮
（只在已保存来源为 *模拟定位* 时出现）：打开一张地图，点一下就把那个点存成**命名选点**，
可以在下拉框里切换、重命名、删除。

- 地图上会画出**学校打卡点**（来自学校 `getDormitory` 返回的基准坐标与半径）、**当前生效的
  选点**与**待保存**标记。标记直接写**选点自己的名字**（例如「杏园三舍」），不再写
  「已保存（地图选点）」这种没有信息量的通用文字；保存前输入名称时，待保存标记会实时显示
  「待保存：杏园三舍」，所见即所存。
- 角标实时显示「距基准点 N 米（范围内/超出范围）」。
- **拖动平移**（按住左键拖动），滚轮或 `放大 / 缩小` 缩放，`回到学校位置` 一键复位，方向键
  平移（Shift 加快），`+/-` 缩放；`在线底图` 可关闭。
- **检测模拟定位** 现在明确报出**用的是哪个选点**：
  「模拟定位检测通过：当前使用选点「杏园三舍」，采样精度约 113 米。基于已保存位置并随机偏移，
  并非当前位置；未提交打卡。」
- **已保存的选点** 下拉框列出全部选点（含各自到基准点的距离），选中即生效；`名称` 输入框配
  `重命名` / `删除`；`保存为选点` 保存地图上当前的点。
- **同名即更新，异名即新建**：名称与已有选点相同 → 更新那个点的位置（提示写「已更新」），
  换一个名称 → 新建一个点。输入框下方直接写着这条规则。

## 定位来源卡片只留必要信息

按用户要求删掉两行纯重复的文案：选择器下方的
「保存后立即全局生效；模拟定位使用本机已保存样本，并非当前位置。重启后保留已保存的选择。」
与来源徽标「当前来源 · 模拟定位（非实时）」。它们要表达的信息在下拉框选项、检测框文案
（`模拟定位（非实时）· …`）和总览页「打卡定位来源」里都已经有了。卡片现在只剩
**选择器 → 保存定位来源 → 检测框 → 检测按钮 →（模拟模式下的地图选点）→ Windows 定位设置**，
间距仍是统一的 12 像素。

## 逻辑：列表是唯一事实来源，样本文件只是镜像

| 文件（`%LOCALAPPDATA%\yoouziauth\dorm`） | 角色 |
| --- | --- |
| `location-points.json` | **唯一事实来源**：`{"points": [{"id","name","latitude","longitude","accuracy","source","saved_at"}], "active": "<id>"}`，最多 12 个；`source` 记录它来自地图选点（`MAP_PICK`）还是本机采样（`SAMPLE`） |
| `location-sample.json` | **只是 active 那个点的镜像**。回放链路（`locate('simulation', …)`）照旧只读这一个文件 |
| ~~`location-sample.previous.json`~~ | **取消**：切换/重新选点不再破坏任何东西，因此没有"要恢复的东西" |

### 自带的默认位置

程序内置两个起始位置（`dorm_points.DEFAULT_POINTS`）：**首次运行**（store 里还没有
`location-points.json`）时把它们写进列表，第一个默认生效。

| 名称 | 坐标 | 来源 | 精度 |
| --- | --- | --- | --- |
| 李园一舍 | 29.823693, 106.422310 | `SAMPLE`（作者本机 Wi-Fi 采样） | 141 米 |
| 杏园三舍 | 29.827409, 106.422742 | `MAP_PICK`（地图选点） | 100 米 |

它们是**普通选点**：可以切换、重命名、删除，删掉之后不会自动复活。`模拟定位` 仍是 opt-in
（默认定位来源是真实定位），所以新装的程序不会自己跑到某个点上打卡。

三条约定的不变量：

1. 列表非空时，`active` 必定指向其中一个点；空列表表示"没有可用位置"。
2. 镜像永远等于 `active` 那个点；列表为空时镜像会被删除（引擎会如实报"没有可用位置"）。
3. **切换、重新选点、重命名都不会删除任何点**；只有明确的"删除"才会移除条目，而且删掉正在
   生效的点时会自动切到列表里的下一个，删掉最后一个时才明确提示"模拟定位暂无可用位置，
   自动打卡会因缺少位置而跳过"。

打开地图或执行任何选点操作时都会先**对账**（`_sync_simulation_points`）：

- 列表里没有、但磁盘上存在的样本会被**收编成选点**而不是丢掉：本机采样样本（含被手工放进
  `location-sample.json` 的旧文件）记为「本机采样样本」；1.5.2 遗留的
  `location-sample.previous.json` 记为「上一个样本」，收编后删除该遗留文件。
- 正在回放的样本优先获得 `active`（它就是程序此刻真正会提交的位置）。
- 列表与镜像不一致时以列表为准重写镜像。

### 1.5.2 的两个缺陷（本次修掉）

1. **选点逻辑会"丢点"**：1.5.2 的 `恢复上一个样本` 只把样本文件换回去，**没有更新选点列表**，
   于是列表说 A 生效、实际提交的是 B，保存过的点看起来就"没了"。根因是同一件事存了两份互相
   独立的状态；现在列表是唯一来源，镜像由列表派生，两者不可能再打架。
2. **第一次保存的点无法重命名**：`renderPoints()` 每次重绘都把名称输入框写回当前选点的名字，
   而地图瓦片是异步加载的，每加载一张就重绘一次 —— 正在输入的新名字被后台重绘冲掉，于是
   "重命名"提交的还是旧名字。现在名称框**只在生效点变化时**刷新，并有专门的回归测试盯着
   （浏览器验收里也复现了"输入后等 3.5 秒瓦片加载"的场景）。

## 坐标基准

| 数据 | 基准 | 处理 |
| --- | --- | --- |
| 地图底图（OpenStreetMap / Web Mercator） | WGS84 | 选点直接以 WGS84 保存 |
| 保存的选点 | WGS84 | 与采样样本同格式，交给原有回放链路 |
| 提交给学校的位置 | GCJ02 | 回放时由 `validate_position` 换算一次，并做既有随机偏移（3–25 米） |
| 学校基准点 | GCJ02 | 展示前用 `gcj02_to_wgs84`（三次迭代，亚米级）换算到地图坐标系 |

选点因此**不会**走第二条换算路径：它和 Windows 采样样本是同一种输入，回放仍是唯一做换算与
偏移的地方，学校看到的 payload 形状不变。

## 底图与隐私

- 底图有**两个来源，按顺序尝试**（`desktop_bridge.TILE_PROVIDERS`，随模型一起下发给界面）：

  | # | 提供方 | 坐标系 | 最高级别 | 地址 |
  | --- | --- | --- | --- | --- |
  | 1 | OpenStreetMap | WGS84 | 19 | `tile.openstreetmap.org` |
  | 2 | 高德地图 | GCJ02 | 18 | `webrd01.is.autonavi.com` |

  两个主机名都在 `desktop_ui/index.html` 的 CSP 里显式列出（`img-src`），其余
  `script/style/font/connect` 仍全部同源 —— 底图只用 `<img>` 加载，页面**不向第三方
  打开任何 fetch/socket**。关闭 `在线底图` 后不再请求任何瓦片。
- **GCJ02 纠偏**：高德的瓦片画在 GCJ02 网格上，而整个选点器工作在同一套 WGS84 里。界面的做
  法是：**瓦片网格与瓦片贴图用 `gcj02(中心)` 投影，而标记与落点仍用 WGS84 中心**。偏移量在一块
  屏幕范围内近似常数，两边的偏移因此互相抵消 —— 校园地物和标记对齐，而选点存下来的坐标始终是
  WGS84。`mapToGcj02` 与 `dorm_location.wgs84_to_gcj02` 是同一套公式，有测试盯着两者的一致性
  （1e-9）。
  这个近似**不是零误差**：GCJ02 偏移场本身随位置缓慢变化（含约 33 km 波长的分量），所以"常数
  平移"会留下一个随视窗变宽而变大的残差。本机在选点器实际用的校园坐标上逐级实测
  （`.scratch/wb2probe/gcj_alignment.py`）：

  | 级别 | 视窗宽 | 残差 |
  | --- | --- | --- |
  | 13（最小） | 11.9 km | **1.13 px** |
  | 15 | 3.0 km | 0.65 px |
  | 17（打开时的默认级别） | 746 m | **0.51 px** |
  | 19（最大） | 187 m | 0.47 px |

  即最坏 1.1 像素、默认级别 0.5 像素（约 0.5 米），远小于 7 像素的标记圆点和 100 米起的打卡
  半径 —— 视觉上分不出来，测试也按"落点仍是 WGS84 中心"来断言，而不是按像素对齐来断言。
- 署名 `© OpenStreetMap contributors` / `© 高德地图` 由画布右下角直接绘制，**跟着真正画出来的
  那个底图走**，并且**只在画布上确实有第三方瓦片时**才画：关闭底图或所有瓦片都失败时，画布上
  只有自己的离线网格，没有第三方地图数据可署名。
- 页面上只在**打开地图后**、且**已保存来源为模拟定位**时显示坐标：命名选点（用户自己选择要
  提交的点）与学校公布的打卡点。**实时 Windows 定位永远不进入界面**，`snapshot()` 也仍然不含
  任何坐标或选点名称（有回归测试守着）。`simulation_map()` 在来源不是模拟定位时直接拒绝。

### 在线底图为什么会「坏」——以及现在怎么自愈

用户报告「在线地图坏了」时，画面是一张**只有网格、没有任何报错**的地图，右下角还挂着署名。
2026-09-27 在本机复现并定位到三层原因：

1. **瓦片"挂住"而不是失败**（真正的病根，也是用户看到的那张图）。在真实 WebView2 里打开选点
   器后，8 张 OSM 瓦片请求 **60 秒内既没有 `onload` 也没有 `onerror`**，一直 pending；同一时刻
   命令行请求 `tile.openstreetmap.org`（以及 `.de` / `.fr` 两个镜像）全部 20–25 秒超时，而高德
   同坐标瓦片 **39 毫秒**返回。旧代码只在 `onerror` 里做任何事，所以连接"挂住"时它**永远不会
   察觉**：地图就这么空着，重开对话框也一样。
2. **OSM 会主动拒绝 App**：不带 Referer 时它返回 HTTP 200 + 一张 `Access blocked` 的 PNG，并在
   响应头写 `x-blocked: No referer sent. Access denied.`。对 `<img>` 来说这是一次成功的加载，
   所以图片处理器同样看不见这件事。
3. **失败没有任何出口**：旧的瓦片表只在 `onerror` 上打一个永久的 `failed` 标记，既不重试，也
   不告诉用户发生了什么 —— 界面上"加载中""被拒绝""离线""用户自己关掉了底图"四种状态长得完
   全一样。

现在的行为：

| 情况 | 现在的表现 |
| --- | --- |
| 单张瓦片失败（`onerror`） | 退避重试（1.2 秒、4 秒，最多 3 次），重试期间不算"失败"，只有用尽次数才记 |
| 单张瓦片**挂住**（既不 load 也不 error） | **每张瓦片有自己的 8 秒期限**（`mapTileDeadline`），到期走与 `onerror` 完全相同的重试/终判路径 |
| 整个底图**失败**（全部 `onerror`） | 自动切到下一个底图源 |
| 整个底图**挂住**（8 秒内一无所获） | 立刻切源（`MAP_TILE_STALL` 快速通道，不必让每张瓦片先跑完重试）—— 这一条才是治"挂住"的关键 |
| 只挂住一部分、其余已经画出来 | 已画出的瓦片留着，挂住的那几张各自到期重试；到期后仍未到就记失败并重画状态行 |
| 所有底图源都用尽 | 画布下方写出「在线底图暂时连不上，已回退离线网格」，并出现 **重试底图** 按钮 |
| 换了底图源 | 写明「已改用备用底图：高德地图。」，署名同步换成 `© 高德地图` |
| 迟到的瓦片在"已回退离线网格"之后到达 | 提示自动消失（画布上已经有真底图了，不能继续说没有） |
| 网络恢复 | `重试底图` 从首选底图重新来过；重开对话框同样会重来 |
| OSM 返回 `Access blocked` 图 | **仍无法自动识别**：那是一次合法的 PNG 加载，`<img>` 读不到 `x-blocked` 响应头，所以既不重试也不切源。此时画布上会直接显示 OSM 自己的「403 Access blocked」海报 —— 至少不是一张无声的空网格；要绕开它需要显式探测，而探测本身已被证明有害（见下） |

**"活着"的判据是瓦片对象，不是状态对象**：`applyMapModel`（保存/切换/重命名/删除选点时都会走）
会**换掉 `mapState` 对象但沿用同一张瓦片表**。所以"这张瓦片还活着吗"必须问
`mapState.tiles[key]===tile`（`mapTileOwner`），而不能问 `mapState===那个旧对象` —— 后者会让所有
在途瓦片同时丢掉重画、重试和切源（用户看到的是：底图缺了几块、没有任何提示、要缩放或重开才好）。
另外计数器只统计**当前缩放级别**的瓦片：`drawMapTiles` 本来就跳过其它级别，署名、切源与状态行
自然也不该被它们左右。

**为什么不做预检（pre-flight）**：第一版实现用 `fetch(HEAD)` 先探测首选底图再决定画谁。实测发
现这正是最坏的做法 —— 在冷启动的 WebView2 里，对 OSM 的**第一个** HEAD 请求会卡到 30 秒超时
（而同一次会话里的瓦片 GET 只要 17 秒），于是探测把**本来能用的**底图判成不可用，健康网络反而
被切到备用源。预检因此被删掉，只保留瓦片自身的表现 + 挂起超时作为判据。

### 落点精度：点哪儿就是哪儿

底图换成 GCJ02 之后，"点下去到底偏多少"必须能被量出来，而不是靠"应该没事"。真实 WebView2 里
的实测（`.scratch/wb2probe/verify_no_offset.py`）：**先算出每个地标在当前底图上被画在哪个屏幕
像素，用真实鼠标点那个像素**，再拿记录的坐标和地标的真值比。地标取中心加上东南西北与对角
7 个方向、110–300 米：

| 底图 | 最坏落点误差 |
| --- | --- |
| 高德（GCJ02） | **0.59 m** |
| OpenStreetMap（WGS84） | **0.59 m** |

两者**一模一样**，说明 GCJ02 纠偏本身贡献了 **0 米**误差（不纠偏的话是 **477.1 m**）。这 0.59 m
全部来自鼠标本身：`offsetX` 只报告整 CSS 像素，而 z17 下 1 个画布像素 ≈ 1.04 米，半个像素的
量化就是 ~0.5 米。同一个脚本还验证了"学校坐标系"这一步：落点经**一次** `wgs84_to_gcj02` 之后
与地标自己在 GCJ02 下的坐标同样只差 0.59 米 —— 也就是说学校看到的就是用户点的那栋楼。

这个量级远小于 100 米起的打卡半径；而修复前这个脚本量到的是 **1.3–2.0 m**，见下面第 9 条。

排查/修复记录（续）：

9. **落点被画布边框斜着拉偏**：`offsetX` 按规范从 **padding 边**起算，而
   `getBoundingClientRect()` 给的是 **border box**；旧代码直接 `offsetX * canvas.width / rect.width`，
   等于把 1 像素边框算进了缩放比，于是越靠右/下偏得越多。真实窗口里量到：画布 720×400、边框
   box 715×398.1、边框 1px、`devicePixelRatio` 2 —— 靠近右边缘的系统性偏差约 1 个画布像素
   （z17 约 1 米），叠加鼠标整像素量化后实测 1.3–2.0 m。现在按 padding box 缩放，实测降到
   0.59 m（纯量化地板）。回归测试 `a click is read through the padding box, not the border box`
   会在三种画布位置上逐一比对像素映射，改回边框 box 立刻失败。


## 校验

- 选点保存时若学校基准点已知，就在消息里给出距离与是否在范围内；**超出半径仍然允许保存**，
  只是明确提示学校可能拒绝（学校 `verify` 仍是最终裁判）。
- 坐标非法（缺失、非数字、越界、NaN）一律拒绝，且不触碰已存样本与选点表；名称为空自动命名
  （`选点 N`），名称清洗控制字符并截断到 24 字，重名改名会被拒绝。
- 打卡进行中或定位检测进行中拒绝修改选点；来源不是模拟定位时同样拒绝。
- 选点表最多 12 个，超出时明确提示先删除；损坏的选点表按空表处理，不影响选点功能。

排查/修复记录：

1. **CSP 静默拦截瓦片**：`img-src 'self' data:` 让瓦片请求全部 `failed: csp`，界面只是"没有
   底图"。现在 CSP 显式列出两个底图源，并且有一条测试**直接从 `desktop_bridge.py` 里读出
   `TILE_PROVIDERS`** 再和 CSP 比对（不是拿第三份硬编码副本自证），改主机名会立刻失败。
2. **`<dialog>` 被 UA 样式限宽**：Chromium 的 UA 样式给 `dialog` 设了 `max-width`，
   `width: min(780px, 94vw)` 因此被压到 440 像素。现在显式写 `width`/`max-width`。
3. **地图无法移动**：只实现了方向键平移，鼠标没有拖动。现在支持拖动平移与滚轮缩放，并抑制
   "拖动结束那一下"被当成落点。
4. **定位来源卡片间距不一致**：`在地图上选择位置` 插在 `检测模拟定位` 与 `Windows 定位设置`
   之间时上方间距为 **0**（其他控件是 11–15 像素），选择器下方的说明文字到保存按钮也是 0。
   现在两处都是 12 像素；验收脚本会测量卡片内所有控件的间距与左右边缘，间距 < 5 像素或边缘
   不齐都会失败。
5. **选点会丢 / 无法重命名**：见上文「1.5.2 的两个缺陷」。
6. **在线底图"坏掉"却毫无提示**：见上文「在线底图为什么会『坏』」。根因是瓦片请求会**挂住**
   （既不 `onload` 也不 `onerror`），旧代码对此完全无感；现在有挂起期限、自动切源、明确文案与
   `重试底图`。第一版的 `fetch(HEAD)` 预检在实测中把健康网络误判为不可用，已删除。
7. **只挂一部分时仍然无声**（第一版修复的漏网之鱼）：第一版只有一个"整块空白才管"的全局挂起守
   卫，只要有一张瓦片画出来它就永久退场，其余的挂住后既不重试也不提示。现在每张瓦片都有自己的
   8 秒期限，全局守卫只作为"一格都没画出来"时的快速通道。
8. **重载会搁浅在途瓦片**（第一版修复引入的缺陷）：保存/切换/重命名/删除选点都会
   `applyMapModel` 重载模型，它**换掉状态对象却沿用同一张瓦片表**，而在途瓦片回调当时按
   `mapState===旧对象` 判断自己是否还活着 —— 于是全部失去重画、重试与切源，底图缺块且没有任何
   提示。现在判据改成瓦片对象本身（`mapTileOwner`），并加了"重载不得搁浅在途瓦片"的回归测试。
